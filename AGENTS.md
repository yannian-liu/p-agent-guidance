# Planist Agent Guidance

This file is the shared source of truth for Planist coding-agent behavior. Project-level `AGENTS.md` files may add narrow project-specific overrides after loading this file.

# Repository Coding Preferences

- Always communicate with the user in Chinese, regardless of whether the user's request is written in Chinese or English. Keep technical terms, code identifiers, commands, API names, and concise keywords such as `compile` in English when that is clearer.
- For now, keep repository operations on the `main` branch by default. When committing authorized work, commit directly on `main` and push to `origin/main`; do not create a feature branch or PR unless the user explicitly asks.
- Treat Planist app projects as pre-release until the user explicitly states otherwise. Do not preserve obsolete development-only persistence identifiers or abstractions merely for local development-install compatibility; prefer names that describe the current responsibility, and update all App, Widget, telemetry, and test call sites together.
- Do not automatically run full test suites (such as unconstrained `xcodebuild test` or UI test runs) after routine code changes, refactors, or reviews. Full test suite execution and simulator launches block conversations and consume significant system resources. Routine validation must rely on fast compilation checks (`xcodebuild build` or syntax checks). Automated test execution should only be run when the user explicitly requests it, or when specifically verifying complex logic with targeted unit tests (`-only-testing`).

# Code Changes and Reviews

Apply the complete checklist to all introduced, changed, or reviewed code, including related behavior, call sites, tests, and supporting files; do not skip pre-existing code. Treat applicable **MUST** items as release-blocking, and evaluate every **SHOULD** item, documenting meaningful exceptions in the final handoff.

## All Files

### MUST

- Follow this mandatory review order without skipping ahead: first verify architecture placement and dependency boundaries; second evaluate logic correctness and overall code quality; last perform the remaining checklist, testing, formatting, editing, and validation work.
- Begin every code review with the architecture phase. Verify that each responsibility, abstraction, type, and file lives in the correct layer, target, module, owner, and directory before evaluating implementation quality or performing any other review activity.
- Apply Clean Architecture during the architecture phase for every introduced, changed, or reviewed file and directory. Keep dependencies pointing inward: presentation and app orchestration may depend on application and domain abstractions, infrastructure must implement ports defined by an inward layer, and domain code must not depend on presentation, persistence, networking, platform frameworks, or concrete infrastructure. Verify that every file is located in the directory that owns its responsibility and abstraction level. Review directory names and ensure each one accurately communicates its architectural layer, feature scope, responsibility, and contents; report names that are stale, ambiguous, misleading, overly broad, overly narrow, or inconsistent with the repository structure, and recommend a clearer name when available. Place each responsibility in the narrowest correct layer and directory, inspect all relevant callers and callees needed to establish the dependency direction, report every misplaced file, incorrectly named directory, cross-layer dependency, or responsibility leak, and correct all such violations when fixes are authorized.
- During the architecture phase, verify that the complete static dependency graph is a directed acyclic graph (DAG), both across architectural layers and within every layer, target, module, and feature. Cross-layer dependencies must follow Clean Architecture and point inward; no dependency cycle may cross a layer, target, module, or feature boundary. Within a layer, dependencies must also have clear one-way ownership and abstraction direction. Sharing a layer does not permit `A -> B -> A`, longer dependency cycles, mutual concrete references, or sibling types orchestrating each other. Prefer a natural top-down graph such as `A -> B -> C`, or place coordination in the narrowest common owner so it depends on sibling collaborators without creating reverse dependencies.
- Runtime results may flow back through return values, errors, events, delegates, callbacks, or protocols owned by an inward layer, but these paths must not introduce a reverse static or concrete dependency, ambiguous state ownership, reentrant control cycles, or lifecycle cycles. Do not introduce pass-through abstractions merely to make the graph appear linear when parallel dependencies are more truthful. Inspect all relevant direct and transitive callers and callees; report and, when fixes are authorized, correct every cross-layer or within-layer dependency cycle, dependency-direction violation, peer-orchestration leak, and unclear ownership relationship.
- After the architecture phase is complete, evaluate logic correctness and overall code quality. Inspect the complete relevant implementation and data flow, including callers, callees, state transitions, failure paths, edge cases, and affected tests, before deciding that the reviewed logic is correct.
- Review the naming of types, protocols, functions, properties, parameters, events, and files. Verify that each name accurately communicates its responsibility, scope, lifecycle, and abstraction level; report names that are stale, ambiguous, redundant, misleading, overly broad, or overly narrow, and recommend a clearer name when an improvement is available.
- Review the ownership and nesting of type declarations, including `struct`, `enum`, `class`, and `actor`. When a type exists only to model a property or implementation detail of one owning type and has no independent domain meaning, nest it inside that owning type and use the narrowest correct access level. This requirement still applies when downstream code reads the property or helper functions accept the nested type; such incidental use does not establish independent ownership. During review-and-repair work, report and correct violations.
- When the initial review finds any problem, report the findings to the user first. Include the priority, affected behavior, evidence, and expected impact before making fixes or proceeding to other review activities.
- Do not silently fix findings during a review. Wait until the findings have been reported before editing code, adding tests, running remediation-specific validation, or continuing with lower-priority cleanup.
- After reporting findings, continue only within the authority granted by the user's request. If the user requested review and repair, reporting the findings authorizes the planned in-scope fixes; if the user requested review only, do not modify code.
- Review and report every valid finding regardless of priority. Do not limit review scope or completion criteria to `P0`, `P1`, or `P2`; `P3` and `P4` findings are also required findings.
- When the user authorizes fixes, resolve every valid finding from `P0` through `P4`, add all applicable tests, and re-review the resulting code. Do not defer lower-priority findings merely because higher-priority findings have been resolved.
- Do not declare a review-and-repair task complete while any known valid finding at any priority remains unresolved. If a finding cannot be resolved within the authorized scope, report it explicitly with the reason, remaining risk, and required next action.
- If the architecture and code-quality phases find no problems, state that result before continuing with the remaining checklist, validation, or other follow-up work.
- Keep Swift function and initializer declarations on one line. Do not vertically split their parameter lists unless the language or compiler requires it.
- Prefer compact one-line function and initializer calls when practical. Wrap call arguments only when a single line would be genuinely difficult to read.
- In `PPComponents`, component chrome colors must come from `PPTokens`. Reuse an existing token when it fits; add a new token only when no existing token expresses the role. Avoid ad hoc hex, system semantic colors, or literal colors for component styling, except for dynamic content colors such as user-selected habit colors.
- Treat app `Store` types as thin `@Published` state shells and ViewModel-facing facades. They should pass through to use cases and refresh published snapshots only; do not put business workflow, auth/sync branching, merge/replace decisions, repository orchestration, or other domain logic in `Store`. Put that logic in use cases or the data layer.
- Verify the logic and all affected call sites for introduced, changed, or reviewed behavior. Check protocols, data flow, persistence compatibility, widgets, tests, previews, and every relevant target.
- Remove unused methods, properties, types, imports, and dead branches. Search for all call sites before deleting code.
- Write comments in English. Replace Chinese comments in every touched or reviewed file with clear English comments.
- Use the narrowest correct access level. Make declarations `private` or `fileprivate` when broader visibility is unnecessary, and do not add new public or internal API without a concrete caller.
- Organize and group declarations by responsibility and follow the surrounding repository conventions. Avoid large formatting-only diffs that obscure functional changes.
- Localize every user-visible string, including errors, alerts, accessibility text, notifications, widgets, menus, and empty states. Handle interpolation, plurals, dates, times, numbers, and text expansion correctly.
- Use English for all localization keys, such as English natural text or English dot-separated identifiers. Do not use localized or non-English text as the key.
- Do not silently swallow errors. Unexpected errors must be recorded through the project's telemetry path whenever technically possible. Expected outcomes such as explicit cancellation may be handled without error reporting when appropriate.
- Never include passwords, authentication tokens, private user content, or unnecessary personally identifiable information in telemetry.
- Ensure every asynchronous flow reaches an explicit success, empty, error, or cancelled state. Never leave the user waiting indefinitely. Recoverable failures must present an understandable message and an appropriate retry or recovery action.
- Add useful telemetry events and context when a user action, failure, or workflow transition is important for diagnosing behavior or understanding product usage. Reuse existing event names and parameter conventions, and avoid accidental duplicate or excessively noisy logging.
- Avoid force unwraps, `try!`, and unexplained `fatalError`. If an invariant truly requires a crash, make the invariant and rationale explicit.
- Review Swift concurrency correctness, including actor isolation, `Sendable`, cancellation, duplicate work, reentrancy, and race conditions.
- Production app code must not introduce `@unchecked Sendable` by default; prefer `actor`, immutable `Sendable` value types, `@MainActor`, or explicit locking/serialization instead, and allow a production exception only for a tiny adapter around a system or third-party API that is known to be thread-safe but not annotated by the SDK, with a short English comment explaining the safety guarantee, no ownership of mutable business state, and explicit reporting to the user during review or implementation. Tests, fakes, mocks, and preview-only support may use `@unchecked Sendable` when needed, but should still keep mutable state isolated, locked, or otherwise deterministically serialized.
- Review lifecycle and memory behavior, including retain cycles, observers, subscriptions, and unstructured or long-lived tasks.
- Check for main-thread I/O, repeated computation, unnecessary rendering or publication, N+1 requests, excessive copying, and other performance regressions appropriate to every introduced, changed, or reviewed path.
- Review UI responsiveness explicitly, including main-thread blocking, expensive work during rendering or scrolling, unnecessary state publications, animation hitches, dropped frames, and any behavior that can make interactions or scrolling feel unsmooth.
- Preserve backward compatibility for persisted data and public behavior unless the requested change explicitly requires a migration or breaking change.
- Require exceptionally comprehensive deterministic unit tests for introduced, changed, or reviewed behavior. During implementation or authorized repair, add or update tests to close every applicable coverage gap. During review-only tasks, do not add or update tests; report every missing or inadequate test as a finding with priority, affected behavior, evidence, expected impact, and the concrete test obligations that must be covered when fixes are authorized. Cover success, boundary, empty, failure, cancellation, retry, concurrency, reentrancy, race conditions, lifecycle, persistence compatibility, telemetry, and regression cases as applicable. Test observable behavior rather than private implementation details, and do not add tests with weak or meaningless assertions merely to increase coverage.
- Write new Swift unit tests with Swift Testing (`import Testing`) by default. Use XCTest only for UI tests or when an existing target constraint makes Swift Testing unsuitable, and document the exception in the final handoff.
- Derive test expectations independently from the acceptance criteria, domain invariants, and intended business semantics. Write tests to challenge and potentially falsify the production logic, not to reproduce its implementation or make the current code pass. When a test exposes a mismatch, re-evaluate the production logic first; never weaken, invert, or copy implementation behavior into the assertion without concrete evidence that the original expectation was wrong.
- Before deciding that test coverage is sufficient, derive an explicit test-obligation matrix from the acceptance criteria and the complete relevant production control flow and data flow. Do not infer completeness only from the existing test suite. The matrix must enumerate every behaviorally distinct observable outcome, conditional branch, `switch` case, guard or early return, thrown or mapped error, state transition, and external dependency outcome. Map every applicable obligation to one or more specifically named tests before declaring the review complete.
- The test-obligation matrix must consider, where relevant: valid and invalid inputs; `nil` and non-`nil`; empty, single-item, and multiple-item collections; duplicates and ordering; values below, at, and above boundaries; minimum and maximum supported values; malformed, missing, stale, and incompatible persisted data; dependency success and failure at every failure-capable boundary; partial success; cancellation before, during, and after suspension; retry exhaustion and eventual success; duplicate submission; reentrancy; concurrent ordering and races; lifecycle termination; date, time-zone, locale, and calendar boundaries; telemetry success and failure behavior; and every reproduced regression condition.
- `As applicable` must never be invoked silently. Every listed test category must either be covered by a named test or marked `N/A` with a concrete, behavior-specific explanation. An unexplained omission, an unmapped test obligation, or a generic statement such as "not relevant" is a release-blocking finding.
- For interacting conditions, cover every independent factor and all behaviorally distinct or high-risk combinations. Do not require meaningless exhaustive permutations when the outcome is provably equivalent; document the equivalence or reduction used to omit combinations.
- After running the relevant tests, inspect changed-line, function, and branch coverage to discover additional gaps. Coverage metrics are supporting evidence only: high or complete line coverage does not establish behavioral completeness, and tests with weak assertions do not satisfy a test obligation.
- The final handoff must include a compact test-obligation summary listing the covered cases, the corresponding test names, any justified `N/A` categories, and any validation that could not be run.
- Place unit-test and UI-test files in test-target directories that mirror the owning production source path and file. For example, tests for `<project-slug>/App/Persistence/Foo.swift` must live in `<project-slug>Tests/App/Persistence/FooTests.swift`, and UI coverage for `<project-slug>/Presentation/Feature/Foo.swift` must live under the corresponding path in `<project-slug>UITests` or the applicable fixture-host UI-test target. Keep cross-component orchestration tests under the orchestration owner, but do not place component-specific tests in broad coordinator, integration, or catch-all files.
- For mocks, spies, and fakes, assert the exact expected number of API or function calls, not merely that a call occurred. In the common case assert exactly one call, and also verify that no unexpected calls occurred.
- Every bug fix must include a regression test when the behavior can be tested deterministically.
- Keep production code free of test-only control paths. Do not add launch arguments, branches, mutable state, APIs, dependency behavior, or production UI solely to satisfy unit tests or UI tests. Use dedicated test targets, test host apps, fixtures, mocks, fakes, dependency injection, or files clearly isolated under test-support boundaries instead; document any unavoidable exception in the final handoff.
- Resolve all compiler, linker, build, and test warnings in every affected or reviewed target. Establish the warning baseline with a clean build when practical, and ensure the final diff introduces no warnings. Report any warning that cannot be resolved, including whether it is pre-existing or originates from a third-party dependency.
- Build every affected or reviewed target (e.g. `xcodebuild build`) to verify compilation and warning resolution before completing an implementation or review. Do not run full test suites or UI tests during routine completion unless the user explicitly requests them or automated testing is necessary and scoped to specific targeted unit tests. If a required validation cannot run, state the reason, the unverified scope, and the resulting risk.

### SHOULD

- Prefer dependency injection for time, randomness, networking, persistence, and other external effects so tests remain fast and deterministic.

## Telemetry

Apply every rule under **All Files** in addition to the rules below.

### MUST

- Treat telemetry as the umbrella term for both product analytics and engineering diagnostics.
- Use `AnalyticsReporting` for product analytics. Product analytics is for understanding user behavior, feature adoption, screen flow, funnel health, and other product questions, and is sent to Firebase Analytics in production.
- Use `DiagnosticsReporting` for engineering diagnostics. Diagnostics is for crashes, non-fatal errors, breadcrumbs, failure context, severity, and repair/debug information, and is sent to Firebase Crashlytics in production.
- Keep analytics and diagnostics conceptually separate even when they share context keys. Product events must not become error reports, and diagnostics must not be used as a product analytics substitute.
- Preserve the Crashlytics breadcrumb bridge from product analytics where useful: important product analytics events should also be available as diagnostics breadcrumbs so crashes and non-fatal errors can be understood in the user's preceding timeline.
- Include the standard telemetry taxonomy whenever technically possible: `telemetry_signal`, `telemetry_layer`, `feature_area`, and `telemetry_session_id` for product events; `diagnostic_severity` and `diagnostic_layer` for diagnostics.
- Use `feature_area` for product breadth, such as `home`, `habits`, `categories`, `account`, `settings`, or `sync`. Use `telemetry_layer` / `diagnostic_layer` for technical depth, such as `presentation`, `auth`, `sync`, `api`, `storage`, or `app`.
- Classify errors at the most precise useful layer. For example, login and session failures are `auth`, real data synchronization failures are `sync`, user-visible UI/ViewModel failures are `presentation`, and startup/runtime failures are `app`.
- Record UI failures with `recordUIError` when the error is user-visible or presentation-driven. Record sync failures with `recordSyncError` when the failure is part of synchronization or retryable outbox work.
- Include enough context to diagnose the behavior without exposing sensitive data: operation name, feature area, screen, entity kind, retryability, attempt count, error domain/code, and non-sensitive identifiers only when they are already safe within the project's conventions.
- Add or update tests for telemetry behavior when adding, changing, or reviewing important user actions, workflow transitions, or failure paths. Verify exact calls and important parameters, including signal, layer, feature area, severity, and retryability where applicable.
- Keep telemetry low-noise. Avoid logging repeated rendering, high-frequency state churn, or duplicate events unless the repetition is intentionally sampled or diagnostically necessary.
- Use stable, query-friendly parameter values whenever technically possible, such as enums, normalized operation names, booleans, counts, and timestamps. Free-form prose parameter values require a concrete diagnostic or product-analysis need.

### SHOULD

- Prefer existing telemetry names and taxonomy before introducing new event names, layers, feature areas, or parameter keys.

## Presentation Layer Files

Apply every rule under **All Files** in addition to the rules below.

### MUST

- Build views from `PPComponents` components whenever a suitable component exists. If no suitable component exists, report the gap to the user before introducing a one-off replacement or expanding the component library.
- Use `PPTokens` for view colors. Do not introduce ad hoc hex values, literal colors, or system semantic colors for application chrome. Dynamic content colors such as user-selected habit colors are allowed. If no suitable token exists, report the missing role to the user.
- Keep the View responsible for rendering state and emitting user intent. Do not perform repository access, networking, persistence, or complex business workflows directly in a View.
- Put testable component configuration and presentation specifications in the ViewModel. Keep purely visual implementation details that are not configuration or presentation specifications in the View or reusable component layer.
- Provide iPhone previews using the default color scheme. Cover every meaningful state and special content combination whenever applicable, including loading, empty, error, loaded, long content, relevant interaction states, and variants with and without elements such as banners. Prefer comprehensive behavioral and content coverage over duplicating device sizes or appearance modes.
- Verify that the feature is functional in loading, empty, error, partial-data, loaded, retry, and cancelled states whenever those states can occur.
- Make empty states actionable when a meaningful next step exists, and make recoverable error states clearly explain what the user can do next.
- Verify layouts in both orientations on iPhone and iPad. Check clipping, truncation, scrolling, overlays, sheets, keyboard interaction, and safe areas rather than only confirming that the view does not crash.
- Handle macOS or Mac Catalyst layout and interaction differences where relevant, including resizable windows, pointer interaction, keyboard navigation, menus, and the absence of touch input.
- Support Dark Mode with correct contrast and without relying on hard-coded appearance assumptions.
- Handle keyboard presentation, focus movement, submit behavior, dismissal, safe areas, scrolling fields into view, and hardware keyboards where relevant.
- Support accessibility, including VoiceOver labels, hints, values, traits, focus order, focus restoration, decorative-element hiding, Dynamic Type through accessibility sizes, and layouts that remain usable with large text. Do not communicate state using color alone.
- Respect Reduce Motion, Increase Contrast, and Differentiate Without Color when the introduced, changed, or reviewed UI uses motion, contrast-sensitive styling, or color-coded meaning.
- Handle navigation, sheets, alerts, deep links, dismissal, back navigation, and repeated taps consistently for every affected flow.
- Prevent duplicate submission for asynchronous actions. Provide appropriate disabled state, progress feedback, cancellation, and retry behavior. Show a loading indicator when latency is perceptible or the user otherwise needs confirmation that work is in progress; avoid unnecessary loading chrome for reliably immediate operations.
- Test asynchronous button state transitions in the ViewModel, including initial, in-progress, success, failure, cancellation, retry, and duplicate-tap behavior as applicable.
- Require stable accessibility identifiers for critical UI-test paths without exposing implementation details unnecessarily.
- Require exceptionally comprehensive UI tests for critical user flows and presentation behavior that are introduced, changed, or reviewed. During implementation or authorized repair, add or update UI tests to close every applicable coverage gap. During review-only tasks, do not add or update UI tests; report every missing or inadequate UI test as a finding with priority, affected behavior, evidence, expected impact, and the concrete UI-test obligations that must be covered when fixes are authorized. Cover meaningful loading, empty, error, partial-data, loaded, retry, cancellation, navigation, sheet, alert, deep-link, keyboard, accessibility, duplicate-submission, and regression scenarios as applicable. Verify both successful outcomes and user-visible recovery from failures while keeping detailed business branching in unit tests where UI coverage would be slow or brittle.

### SHOULD

- Use haptics when they improve feedback for taps, selections, success, warnings, destructive actions, or other meaningful interactions. Routine button feedback is acceptable when consistent with the existing product experience. Avoid duplicate haptics, feedback that conflicts with the outcome, excessive feedback during rapid/repeated interaction, or haptics that add noise without clarifying the interaction.
